# Разбор к защите

Все команды ниже выполняются из папки starter. Нужен Python 3.10+ без сторонних библиотек.

## Что показать преподавателю

| Команда | Ожидаемое время | Что доказывает |
| --- | --- | --- |
| python3 step1_sync.py | около 10 с | обычный цикл выполняет работу последовательно |
| python3 step2_sequential.py | около 10 с | async сам по себе не добавляет конкурентность |
| python3 step2_async.py | около 1 с | gather позволяет перекрыть ожидания |
| python3 step3_server.py | около 7 с | короткие запросы стоят за длинным |
| python3 step3_server_async.py | около 5 с | короткие запросы заканчиваются через 0,5 с |

Время приблизительное: планировщик ОС и нагрузка добавляют задержки. sleep моделирует ожидание; настоящей базы данных и сетевого сервера здесь нет.

## Как объяснить код

В шаге 1 work печатает начало, блокирует текущий поток на секунду через time.sleep и печатает завершение. main вызывает work десять раз. Ожидания складываются: 10 × 1 с. Во время sleep поток не крутит вычислительный цикл; процессор может выполнять другую работу.

В шаге 2а async def объявляет корутинную функцию. Вызов work(n) создаёт объект корутины, а await work(n) выполняет её и ждёт завершения. main не переходит к следующей итерации, пока текущая work не закончится. Во время asyncio.sleep цикл событий свободен, но других рабочих задач мы ещё не запустили.

В шаге 2б сначала создаётся список из десяти объектов корутин. Их тела на этом этапе не выполняются. Звёздочка в gather(*coroutines) передаёт элементы списка отдельными аргументами. gather планирует корутины как задачи и позволяет им продвигаться конкурентно. await gather ждёт завершения всей группы.

Каждая work печатает start и приостанавливается на asyncio.sleep. Цикл событий запускает следующую готовую задачу. Примерно через секунду таймеры позволяют продолжить задачи после await, и появляются done. Ожидания перекрываются: общее время близко к самому длинному ожиданию.

В шаге 3 логика та же, но ожидания разные. В синхронной версии carol начинает работу после alice и bob: 0,5 + 5 = 5,5 с; ответ получает на 6-й секунде. В асинхронной версии все начинают почти сразу: carol заканчивает на 0,5 с, bob — на 5 с. Сам запрос bob всё ещё занимает 5 секунд.

## Вопросы, на которых легко ошибиться

- Корутина и Task — разные вещи. Корутина описывает приостанавливаемое выполнение; Task планирует её выполнение в event loop и хранит результат или исключение.
- asyncio.run(main()) создаёт цикл событий, выполняет main и закрывает цикл. В этих примерах его вызывают один раз из точки входа.
- Один поток может продвигать много задач. В шаге 2б есть десять рабочих Task и задача main. Ускорение получается за счёт перекрытия ожидания, а не одновременного исполнения Python-кода на десяти ядрах.
- await не обязательно переключает задачи. Переключение возникает, если ожидаемая операция действительно приостанавливает выполнение; уже готовый результат может быть получен сразу.
- Без await вызов work(n) не печатает start/done. Неиспользованная корутина вызывает RuntimeWarning: coroutine 'work' was never awaited. Адрес объекта в print зависит от запуска.
- create_task планирует отдельную корутину и возвращает Task. gather собирает группу ожидаемых объектов и ждёт их вместе; результаты возвращаются в порядке аргументов, даже если задачи завершались в другом порядке.
- Вариант с create_task: сначала создать все задачи в цикле, потом ожидать их в другом цикле. Если создавать и сразу ожидать каждую задачу в одном цикле, снова получится последовательное выполнение.
- Порядок завершения независимых задач с близкими задержками не стоит считать гарантией программы.
- Этот сервер — модель. В синхронном цикле обработчик carol ещё не вызван; о реальной очереди сетевых соединений по этому коду судить нельзя.

## Дополнительный шаг 4

    python3 step4_blocking.py --mode blocked
    python3 step4_blocking.py --mode thread
    python3 step4_blocking.py --mode process
    python3 step4_blocking.py --mode thread --heavy bob,dave,eve
    python3 step4_blocking.py --mode process --heavy bob,dave,eve

В handle_request сначала выводится принятие запроса. Обычные клиенты ждут asyncio.sleep. Для тяжёлых клиентов выбранный режим определяет, где выполняется heavy_compute:

- blocked вызывает функцию прямо в потоке event loop. До её завершения остальные задачи не могут продолжиться.
- thread передаёт функцию в рабочий поток через asyncio.to_thread. Event loop получает возможность обслуживать короткие задачи.
- process передаёт функцию в пул процессов через run_in_executor. Отдельные процессы могут выполнять вычисления на разных ядрах.

В main пул открывается через with и закрывается после завершения запросов. Он передаётся обработчикам параметром. heavy_compute объявлена на уровне модуля, чтобы её можно было передать процессу. Защита if __name__ == "__main__" не позволяет дочернему процессу повторно запускать программу при импорте.

Для обычного CPython с включённым GIL несколько потоков делят исполнение Python-кода: они чередуются, а не обязательно заканчиваются строго по очереди. Один вычислительный поток всё равно освобождает event loop от непрерывного вызова: интерпретатор периодически переключает потоки. Это сохраняет отзывчивость, но не обещает ускорения вычислений или точного ответа на 0,5 с.

Три процесса могут ускорить три вычисления, если доступны ядра. На результат влияют запуск процессов, нагрузка и ограничения CPU. Поэтому обещать ровно трёхкратное ускорение нельзя. Для сборок Python без GIL поведение потоков может отличаться.

Синхронный сетевой запрос обычно достаточно вынести в поток: большую часть времени он ждёт ввод-вывод. Тяжёлый цикл на Python в обычном CPython лучше распараллеливать процессами.

## Короткое объяснение своими словами

«Я сравнил последовательное и конкурентное ожидание. В обычном цикле и в цикле с await следующая работа начинается после предыдущей. Через gather я запускаю всю группу: когда одна задача ждёт, цикл событий продвигает другие. Поэтому ожидания перекрываются. В примере сервера короткие запросы больше не стоят за bob. Если же вызвать тяжёлую синхронную функцию внутри корутины, она займёт поток цикла событий; для неё нужен отдельный поток или процесс».

Перед защитой закрой этот файл и попробуй сам предсказать первые строки каждого запуска. Затем объясни, что изменится, если заменить asyncio.sleep на time.sleep. Если можешь обосновать порядок и время без подсказки, основная идея понятна.
